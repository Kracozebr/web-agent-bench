# Подтверждение вывода владельцем

Дата: 22 октября 2026 года. Пользователь выбрал подпись привязанного кошелька
либо passkey для аккаунта только с Google. Это продуктовое решение и проект
контракта, не нормативная OpenSpec, реализация или проверенный сценарий.
CDP API уже выбран пользователем как подписант реальных переводов; подтверждение
конкретного вывода владельцем — отдельная граница авторизации платформы.

## Согласованные правила

Владелец входит через Google или кошелёк; способы входа можно связать. Он выводит
доступный денежный остаток на любой указанный адрес USDC в Base, включая биржу.
Адрес назначения не обязан совпадать с кошельком входа и не требует доказательства
владения подключением. Бонусы не выводятся. После подтверждения владельцем перевод
исполняется автоматически без дополнительного одобрения администратора; сетевую
комиссию в MVP оплачивает платформа. Агентские credentials не разрешают вывод.

Начальный минимум — 1 USDC, порог меняет администратор. Если весь доступный для
вывода денежный остаток меньше порога, разрешён его полный вывод; частичный вывод
ниже порога и нулевая сумма не разрешены. Для исключения считаем только свободный
денежный остаток с подтверждённым `finalized`, без бонусов и резервов. Изменение
остатка не разрешает платформе изменить сумму заявки без нового подтверждения.

## Выбранный вариант

- Владелец с привязанным кошельком подтверждает конкретный вывод свежей подписью
  структурированных данных. Используется кошелёк, владение которым уже связано
  с аккаунтом, а не произвольный адрес из входящего запроса.
- Владелец без привязанного кошелька настраивает passkey и подтверждает вывод через
  системное окно: биометрия, PIN или аппаратный ключ в зависимости от устройства.
  Наличие Google-входа не требует заводить отдельный EVM-кошелёк только для вывода
  на адрес биржи в выбранном варианте.
- Если у аккаунта оба способа подтверждения, сервер разрешает только ранее
  настроенный допустимый метод, привязанный к текущей заявке. Клиент не может
  заменить проверку обычным подтверждением «я уже вошёл».

Рассмотренная альтернатива — обязательный passkey для всех выводов — не выбрана.
У аккаунта с привязанным кошельком доступна подпись этого кошелька, даже если
текущий вход выполнен через Google. Общий вход и адрес назначения сами по себе
не заменяют подтверждение конкретного вывода.

Better Auth документирует passkey/WebAuthn, в том числе обязательную проверку
биометрией/PIN через `userVerification: required`; значение по умолчанию —
`preferred`. Плагин — основа интеграции, а не готовая привязка к выводу. Точные
версии и поддержка устройств пилота ещё не проверены.
[Better Auth Passkey](https://better-auth.com/docs/plugins/passkey).

Для кошелька предлагается отдельный EIP-712 intent вывода, отличающийся от входа
SIWE. Это подпись согласия на действие платформы, не перевод средств из личного
кошелька и не token approval/permit. Сам EIP-712 не обеспечивает защиту от повторов:
её реализует платформа. [EIP-712](https://eips.ethereum.org/EIPS/eip-712),
[Better Auth SIWE](https://better-auth.com/docs/plugins/siwe).

## Общий контракт для будущей спеки

Сервер создаёт неизменяемую заявку: владелец, сумма, Base/USDC, полный адрес,
идентификатор операции, одноразовый challenge и срок подтверждения. Экран явно
показывает детали. Замена суммы/адреса требует новой заявки и подтверждения.

У passkey сервер связывает случайный WebAuthn challenge с хешем этой заявки и
проверяет владельца credential, origin/RP, подпись, требуемую user verification
и однократность. Нельзя трактовать обычный успешный login как согласие на любой
последующий вывод. Системное окно passkey не обязательно показывает сумму/адрес;
детали показывает приложение, а сервер обеспечивает неизменность привязки.

Проверка подтверждения, его однократное использование и постановка одного
авторизованного вывода в исполнение должны быть согласованы транзакционно.
Повтор того же запроса возвращает ту же операцию; не создаёт новый платёж.
Денежный резерв защищает от одновременной траты/вывода; бонусный остаток не участвует.
Перед подписью через CDP сервер вновь проверяет соответствие исполняемой операции
подтверждённой заявке. Таймаут после отправки требует сверки, не нового перевода.

Разделение входа и разрешения операции, серверная проверка существенных данных,
короткоживущее уникальное подтверждение и защита от повторного использования
опираются на рекомендации OWASP. Это проект нашего протокола на их основе,
а не доказательство соответствия реализованного приложения.
[OWASP Transaction Authorization](https://cheatsheetseries.owasp.org/cheatsheets/Transaction_Authorization_Cheat_Sheet.html).

## Настройка и восстановление

Пользователь подтвердил следующие правила:

- Настроить хотя бы один способ подтверждения вывода до показа реквизитов первого
  денежного пополнения. Бесплатная регистрация, бонусы и разрешённые бонусные
  действия не требуют этой настройки. Это ограничение интерфейса выдачи реквизитов,
  не возможность остановить перевод сети на уже известный адрес.
- Использовать заранее привязанный резервный метод при утрате основного; если
  утрачены все методы, направлять случай на ручной разбор администратором вместо
  автоматического сброса подтверждения одним входом Google. Замена требует
  отдельной проверки владения. Обычные подтверждённые выводы остаются автоматическими.

Оба правила согласованы пользователем. Ручной разбор относится к восстановлению
метода; он не заменяет подтверждение отдельного вывода владельцем и не означает
автоматическое одобрение замены без доказательств владения.

На время ручного восстановления пользователь подтвердил приостановку новых
выводов до завершения проверки владения. Услуги и бонусы остаются доступны по
обычным правилам; восстановление не является разрешением на отдельный перевод.

Точный протокол начальной привязки, резервного метода, отключения старого и
проверок при ручном восстановлении ещё требует дизайна. Нельзя выдавать новый метод
подтверждения лишь потому, что в браузере осталась сессия. Начальная настройка
и замена существующего метода должны иметь явно определённую проверку владельца.
Резервный метод и ручной разбор выбраны; конкретные проверки recovery ещё не определены; он не заменяет подтверждение обычного
вывода и не вводит ручное администраторское согласование каждого перевода.

Метод ограничивает полномочия платформенного агента и подтверждает контроль над
средством авторизации. Он не доказывает, что действовал биологический человек,
и не обещает защиту от любого поведения владельца, его устройства или кошелька.
Это соответствует уже обсуждённой границе «только владелец».

Следующий шаг: определить конкретные проверки настройки/восстановления и
политику подтверждения сети, затем перенести требования в OpenSpec платёжной интеграции.
Исполняемых тестов и реальных заявок на вывод этот документ не создаёт.
