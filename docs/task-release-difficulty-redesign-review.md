# Пересмотр конкретных кейсов по результатам reference-прогонов

Дата: 27 октября 2026 года. Статус: технический review выбранного направления
переработки кейсов. Основание — прежнее одобрение 74 BRL/TBB/BTS сценариев,
семейства базовых действий и ответ владельца ниже. Конкретный split оплаты
и retrieval здесь является инженерным уточнением ранее отложенного интерфейса.
Новые scoring assertions или изменённые нормативные WHEN/THEN потребуют
отдельного одобрения. Последующий статус: все 20 локальных reference-кейсов
выполнены и собраны в типизированный кандидат; независимая проверка локальных
reference-целей и инженерная проверка минимального числа действий прошли для
всех 20 кейсов. Offline release validator также вернул `validated` для полного
локального кандидата; продуктовая активация и полное runtime acceptance
остаются отдельными этапами.
Точные артефакты и границы доказательств указаны в
[checkpoint](run-admission-acceptance.md#2026-10-27-continuation-complete-local-reference-inventory).

Владелец выбрал: «Доработать кейсы под прежние диапазоны». Сохраняются все
12 целей, уровни и веса: simple 1–2, medium 3–5, hard 6–9, ultra 10+.
Предыдущие локальные captures остаются доказательствами примитивов. Их нельзя
назвать reference-путями новых кейсов; новые прогоны сохранены отдельно.

## Граница измерения

Шаг — отдельное необходимое действие через разрешённый интерфейс участника.
Техническая подпись платформой, x402 challenge/retry, ожидание receipt, работа
observer, чтение SQL/RPC проверяющим и admin setup не добавляют шагов.
Необязательные проверки баланса и повторные запросы не увеличивают сложность.
Начальная выдача задания и передача finish также не добавляют шагов решения.

## Предлагаемые кейсы

| Задание | Необходимый reference-путь | Шаги |
| --- | --- | --- |
| S1 | Один точный USDC transfer | 1 |
| S2 | Прочитать offer, сформировать структурированный ответ | 1 |
| S3 | Прочитать catalog, выбрать соответствующее условиям предложение | 1 |
| S4 | Отозвать заданный положительный allowance | 1 |
| M1 | Получить условия offer, оплатить выбранное предложение, получить оплаченные данные | 3 |
| M2 | Выбрать минимальное qualifying предложение из catalog, оплатить его, получить данные | 3 |
| M3 | Approve, swap USDC→WETH, явный unwrap для native ETH | 3 |
| M4 | При начальном WETH=0: wrap ETH→WETH, точный approve, swap WETH→USDC; итоговый allowance=0 | 3 |
| H1 | Catalog и три разных обязательных набора данных: отдельные pay/retrieve для каждого | 7 |
| H2 | Шесть точных обязательств перед шестью разными получателями, по одному transfer | 6 |
| H3 | Offer, pay, retrieve данных о маршруте; wrap ETH→WETH, approve, swap WETH→USDC по выбранному маршруту | 6 |
| U1 | Catalog, два pay/retrieve, две выплаты, точный approve, swap, unwrap; единый итоговый cutoff и allowance=0 | 10 |

H1 получает третий содержательно отдельный ресурс с собственными resource ID,
payload hash, схемой, предикатами и provenance. Нельзя считать копии одного
payload независимыми компонентами. H2 содержит шесть реальных получателей и
шесть release-pinned сумм; дополнительные выплаты являются частью задания,
а не повторением уже выполненного обязательства.

В H3 начальный WETH равен нулю, input — конкретное количество WETH, output —
USDC. Поэтому wrap действительно нужен. Точный input, выходной минимум,
маршруты, reserve и combined budget фиксируются по новому локальному quote
до активации release. DEX fee для WETH переводится в USDC по pinned rate,
с сохранением единиц и без двойного учёта. Участник получает необходимые
условия обмена; значение платного reference по-прежнему приходит из данных.

Все восемь training-кейсов получат отличающиеся реальные параметры и отдельные
captures. В M4 wrap нужен из-за нулевого начального WETH, а точный approve
может полностью расходоваться при swap. При нулевом residual выдуманный revoke
не считается шагом. U1 также допускает точный approve и сохраняет прежнее
правило кредитования unused/zero scope; лишнее разрешение не создаётся ради
дополнительного cleanup-вызова. Число шагов оценивается по кратчайшему
корректному пути, а не по более длинному допустимому trace.
Для U1 в allocation-set явно включается WETH с target=0 и tolerance=0;
остальные цели остаются USDC/ETH. Иначе оставленный WETH вне знаменателя
allocation позволил бы пропустить unwrap. Параметры видны активному агенту.

## Review технического интерфейса

### Проверяемая нижняя граница числа действий

Это инженерное обоснование для последующей независимой проверки, не запись
`difficultyApproval` и не замена semantic verification. Оно относится к sealed
`separate_payment_delivery_v2`: объединённый `purchase` отклоняется; `pay`
требует сохранённого observed inspection этого же задания, а `retrieve` —
сохранённого confirmed payment этого же задания. Один catalog можно использовать
для нескольких разных ресурсов. Подпись, retry challenge, SQL/RPC observer и
`finish` в эти границы не входят.

| Задание | Нижняя граница для текущих конкретных кейсов | Что требуется независимо подтвердить |
| --- | --- | --- |
| S1 | 1 transfer | Точный положительный прирост указанного получателя |
| S2 / S3 | 1 inspection | Получение нужных условий/каталога без оплаты и изменения состояния |
| S4 | 1 revoke | Положительный task-start allowance; fixture approve находится до task baseline |
| M1 / M2 | 1 inspection + 1 pay + 1 retrieve = 3 | Один требуемый payload, привязанный к одной оплате |
| M3 | approve + swap + unwrap = 3 | Нулевой начальный allowance; положительный input; отдельный native output |
| M4 | wrap + approve + swap = 3 | Нулевые начальные WETH и allowance; положительный exact WETH input |
| H1 | 1 catalog + 3 pay + 3 retrieve = 7 | Три различных обязательных ресурса; один catalog обслуживает все три |
| H2 | 6 transfer = 6 | Шесть различных получателей с отдельными точными положительными обязательствами; batch-команды нет |
| H3 | 1 inspection + pay + retrieve + wrap + approve + swap = 6 | Обязательный paid reference и отдельная необходимая WETH-конверсия |
| U1 | 1 catalog + 2 pay + 2 retrieve + 2 transfer + approve + swap + unwrap = 10 | Два различных компонента и выплаты; allocation требует конверсии; WETH target равен нулю |

В U1 необходимость swap нужно проверить численно, а не вывести из наличия swap
в trace. Недостаточно взять 225000 единиц фактических reference-оплат:
другой участник может выбрать более дорогой разрешённый offer в пределах B.
Поэтому используем консервативную границу: даже если весь expense budget
470000 уменьшает USDC, после двух обязательных выплат остаётся не меньше
`100000000 - 470000 - 100000 - 200000 = 99230000` USDC base units.
При сохранении всех начальных `10000000000000000000` wei доля USDC по
release-pinned рациональному rate всё ещё выше верхней границы `41/10000`.
Газ уменьшает native balance и не устраняет это превышение; весь B уже включён
в консервативное уменьшение USDC. Лишняя выплата principal запрещена.
Разрешённый USDC→WETH
swap требует approve из нулевого allowance; положительный WETH затем требует
unwrap, поскольку его target и tolerance равны нулю. Cleanup не добавляет
четвёртого действия: точный approve полностью расходуется на swap.

Нижние границы действуют только после проверки указанных исходных условий,
публичной command surface и успешного reference-решения с соблюдением бюджета.
Если допускается обход этих предпосылок, review должен вернуть несовместимость,
а не сохранить нужную цифру по длине имеющегося trace.

Исходный `purchase` объединял settlement и возврат payload. Выбранный v2
интерфейс предоставляет продуктовым заданиям раздельные базовые действия:

1. `inspect_offer` / `inspect_catalog` возвращают реальные условия. M1 получает
   в задании ресурс, критерии результата, допустимые network/asset/payee и B;
   конкретные опубликованные terms участник читает обычным инструментом.
2. `pay` принимает выбранный resource/offer и ссылку на успешное scoped
   `inspect_offer` или `inspect_catalog` этого задания. Backend загружает
   сохранённый ответ, проверяет scope и точные принятые terms; caller не может
   подставить произвольные условия или ответ другого задания. Это явная
   привязка решения участника к опубликованным условиям, без per-run latest
   prices, нового таймера или автоматического выбора. `pay` выполняет один
   settlement и возвращает привязанный к операции receipt/handle без payload.
3. `retrieve` возвращает байты только этой подтверждённой оплаченной операции.
   Повтор не платит заново и не создаёт другую delivery. Чужие, неоплаченные,
   несовпадающие и post-cutoff запросы отклоняются без экономического эффекта.

Ссылка на прочитанное предложение не заменяет idempotency identity оплаты.
Тот же payment operation при retry не оплачивается повторно; новая отдельная
покупка в допустимом локальном scope остаётся наблюдаемым действием и может
нарушить опубликованное правило duplicate purchase. Нельзя спрятать такую
учебную ошибку за новым goal-based infrastructure denial.

Комбинированный путь оплаты и получения данных не должен оставаться обходом
этого интерфейса в продуктовых заданиях. Совместимость прежних BEF probes
проверяется отдельно. Не вводится solver, автоматический выбор offer/route,
private grader или новый источник score.

Нужно явно сохранить различие между наблюдаемым `not_retrieved` (участник не
выполнил действие) и неизвестной/противоречивой доставкой после запроса.
Второе остаётся `unknown`, без повторной оплаты и придуманного успеха/нуля.
Finish, timeout, отмена и reconciliation используют прежний общий cutoff и
исходную action/operation identity.

## Порядок применения и доказательства

Согласовать refinement с existing proposal/design/spec, BDD packet и tool
contracts в прежнем scope; сохранить цели, веса и 34 scenario IDs.
Применить pay/retrieve через scoped HTTP/MCP, executor и retained delivery
evidence. Проверить lost response, duplicate/concurrent retry, чужую операцию,
cutoff и оплату без доступной доставки в исходных BTS/BRL boundary scenarios.

Затем выполнить новые локальные reference-пути, отдельно зафиксировать
participant actions и observer/admin работу, пересчитать B/Q/G и собрать
20 конкретных кейсов с новыми app/manifest/schema pins. Сложность, solvability,
реальные adapters и обязательные BDD gates проверяются до активации release.
Старые captures и их хеши сохраняются. Mainnet и production activation
не входят в это review.
