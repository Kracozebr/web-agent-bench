# Подтверждение реальных переводов Base

Дата проверки источников: 22 октября 2026 года. Это исследование и предложение
с принятой пользователем продуктовой политикой, не нормативная OpenSpec или измерение нашей
инфраструктуры. Реальные депозиты/выводы, RPC-проверки и интеграция CDP не выполнялись.

## Что уже выбрано

Постоянный EOA на аккаунт, CDP API как подписант первого MVP, автоматическое
зачисление после проверки перевода и сети, без ввода хеша пользователем. Вывод —
на указанный владельцем адрес USDC в Base после свежей подписи привязанного
кошелька либо passkey для Google-only аккаунта. Бонусы в вывод не входят.

Настройка подтверждения требуется до выдачи первых реквизитов денежного пополнения;
бесплатная регистрация/бонусные действия доступны без этого. При утрате методов
используется заранее настроенный резервный, иначе — ручной разбор с проверкой
владения; это не администраторское одобрение каждого обычного вывода.

Пользователь выбрал доступность для услуг после `safe`, для вывода — после
`finalized`. Стадию определяет проверенное состояние сети, а не таймер ожидания.

## Наблюдаемые стадии и ориентиры

| Стадия | Что означает | Ориентир Base из документации |
| --- | --- | --- |
| Включение в L2-блок | Sequencer включил транзакцию в блок | Около 2 секунд |
| Публикация batch в L1 | Данные batch поступили в Ethereum | Около 2 минут |
| Финальность batch в L1 | Соответствующие данные опираются на финализированный Ethereum-блок | Около 20 минут |

Это опубликованные ориентиры, не SLA, измерения нашего приложения или таймеры,
по истечении которых можно считать перевод подтверждённым. Состояние определяется
наблюдением сети. [Base Transaction Finality](https://docs.base.org/specifications/transactions/transaction-finality).

В OP Stack используются статусы `unsafe`, `safe`, `finalized`; RPC-теги `safe`
и `finalized` отражают соответствующие головы цепочки. `safe` ещё не равен
окончательной финальности Ethereum. Для внешних действий по поступлению средств
документация OP Stack рекомендует дождаться как минимум `safe`. Поддержка и
актуальность этих наблюдений у выбранного RPC ещё требуют проверки.
[OP Stack: Transaction Finality](https://docs.optimism.io/op-stack/transactions/transaction-finality).

## Принятый выбор

**Оплата услуг после `safe`, вывод соответствующих средств после `finalized`.**

В кабинете отдельно показываются обнаруженное поступление, доступная для услуг
денежная сумма и доступная для вывода денежная сумма. Это права расходования
одного cash-баланса, а не ещё одна валюта или конвертация бонусов. Статусы должны
объяснять ожидание сети, не скрывая его под сообщением «средств недостаточно».
Бонусы сохраняют отдельный учёт по согласованным правилам.

Преимущество — раньше доступны сообщения/темы форума и прогоны без призов.
Оператор принимает остаточный риск публикации/услуг до полной финальности.
Нужны дополнительная проверка доступности к выводу и консервативный учёт
расходования/резервов при смешении поступлений разных стадий. Нельзя освобождать
к выводу непроверенное поступление, просто прибавив его к старому остатку.
Будущие призовые режимы требуют отдельной политики; это решение их не запускает.

**Более простой вариант:** зачислять для услуг и вывода только после `finalized`.
До этого показывать поступление как ожидающее без расходования. Он сокращает
сложность учёта доступности и ожидание риска до финальности, но первая оплата
после нового депозита обычно потребует большего ожидания. Пользователь может
использовать уже доступные средства/бонусы по их обычным условиям.

Вариант ожидания `finalized` для обоих действий сохранён как рассмотренная
альтернатива; выбран первый вариант. Порог только по числу секунд или L2-блоков
не подменяет выбранное наблюдаемое состояние сети.

## Общая граница будущей платёжной спеки

- Проверять разрешённую сеть и точный адрес токена, успешное исполнение,
  получателя из закреплённой карты аккаунтов, событие/сумму и блок. Одно название
  `USDC` или переданный клиентом хеш не являются основанием для начисления.
- Сохранять идентичность события перевода, хеш/номер блока, наблюдаемую стадию,
  источник RPC и сырой путь/хеш доказательств. Один хеш транзакции может содержать
  несколько событий; повторное сканирование не создаёт ещё одно зачисление.
- Отделять обнаружение, доступность для услуг, доступность для вывода и sweep.
  Перемещение собственных средств между адресами не является новым депозитом.
- Если нужный RPC-тег недоступен, RPC отстаёт или наблюдения противоречат друг другу,
  оставлять состояние неизвестным/ожидающим и запускать сверку; не переходить
  молча на более раннюю стадию и не кредитовать по времени ожидания.
- Обрабатывать потерю каноничности до выбранной финальности без удаления исходных
  наблюдений. Если услуги уже потреблены, нужен явный путь расследования и учёта
  отклонения, а не фиктивный положительный депозит или повторная внешняя транзакция.
- Для вывода различать авторизацию, резерв, отправку, наблюдаемое исполнение и
  финальность. Таймаут отправки не разрешает новый платёж; сначала сверять
  исходную операцию/nonce/известные хеши. Точные переходы войдут в OpenSpec.

Гарантии выше — предлагаемое поведение системы для проверки, не результаты
уже выполненных тестов. Фактические комиссии, задержки наблюдателя, политика
RPC/failover, параметры резервирования и численные лимиты ещё не выбраны.

Подготовлен [пакет платёжной интеграции](../openspec/changes/base-account-payments/proposal.md):
12 требований и 20 обязательных планируемых BDD-сценариев. Отдельная проверка
CDP/Base Sepolia требует реального тестового подключения; локальные входные
данные финальности не доказывают работу Base.

Пользователь подтвердил правила исключительных случаев:

- При доказанной потере каноничности уже зачисленного депозита приостанавливаем
  новые денежные расходы и вывод затронутого аккаунта до сверки. История и
  расхождение по уже потреблённым услугам сохраняются; другие аккаунты не затрагиваются.
  Недоступный или отстающий RPC сам по себе не доказывает потерю депозита.
- Пока идёт ручное восстановление утраченного метода подтверждения, приостанавливаем
  новые выводы; услуги и бонусы остаются доступны по обычным правилам. Восстановление
  не заменяет свежего подтверждения конкретного вывода. Точная проверка владения
  и порядок открытия/закрытия обращения ещё требуют дизайна.
