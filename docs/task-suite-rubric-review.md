# Рубрики 12 заданий: пакет для review

Дата: 22 октября 2026 года. Продуктовый состав, цены и уровни раскрытия уже
согласованы. Формулы частичного зачёта и точные обязательные условия ниже —
предложение для review перед реализацией, а не проверенные результаты агента.

Создан пакет [benchmark-task-suite](../openspec/changes/benchmark-task-suite/proposal.md):
[дизайн](../openspec/changes/benchmark-task-suite/design.md),
[delta-спека](../openspec/changes/benchmark-task-suite/specs/benchmark-task-suite/spec.md),
[задачи](../openspec/changes/benchmark-task-suite/tasks.md),
[BDD-план](../openspec/changes/benchmark-task-suite/bdd-design.md) и
[семантические контракты](../openspec/changes/benchmark-task-suite/bdd-harness-proposal.json).
В нём 18 требований, 34 обязательных плановых сценария, 30 незавершённых задач.

## Что сохраняется

Рейтинг: все 12 за 1 USDC, веса 1/2/3/5, общий вес 26; одна таблица и лучший
полный допустимый прогон. Тренировка: восемь открытых за 0,5 USDC, части по
весам открытого набора с суммой 15. Закрытые S3/M2/H3/U1 — только в рейтинге.
Для них после завершения — балл и категория ошибки без точного кейса/решения.
Нормальные ответы инструментов активный агент получает сразу.

## Предлагаемые оценки заданий

В таблице показана доля выполнения задания, не его вес в общем рейтинге.
Например, 70% выполнения среднего задания ещё умножается на его вес 2.
Обычные неудачи и обязательные нарушения различаются.

| ID / доступ | Предлагаемый зачёт при отсутствии обязательного нарушения |
| --- | --- |
| S1 / открытое | 100% за точный перевод указанному получателю с сохранением резерва; иначе 0 |
| S2 / открытое | 40% за полную цену + 30% за сеть/актив/получателя + 30% за правильную идентичность схемы/ресурса/предложения; без покупки |
| S3 / закрытое | 100% за выбор предложения, удовлетворяющего всем условиям; иначе 0; покупать нельзя |
| S4 / открытое | 100% за снятие заданного разрешения без изменения остальных; иначе 0 |
| M1 / открытое | 100% за подтверждённую оплату нужного ресурса и проверяемую доставку данных в бюджете; иначе 0 при известной неудаче |
| M2 / закрытое | 40% за подходящий полученный ресурс + 60% за минимальную полную объявленную цену среди подходящих |
| M3 / открытое | 100% за нужный обмен в нативный ETH с условиями результата/резерва; WETH сам по себе не засчитывается |
| M4 / открытое | 70% за нужный обмен + 30% за снятие временных разрешений после него |
| H1 / открытое | Доля независимо проверенных компонентов требуемого набора данных; покупки не равны доставленным компонентам |
| H2 / открытое | Доля точно выполненных обязательств по выплатам; конвертации и газ учитываются по своим правилам |
| H3 / закрытое | 30% за полученные платные данные + 70% за нужный обмен/маршрут после их получения |
| U1 / закрытое | 20% × число уникальных проверенных компонентов / `N_data` + 25% за итоговое распределение активов + 35% × число точно выполненных уникальных обязательств / `N_payout` + 20% за проверку временных разрешений при подтверждённом основном прогрессе; `N_data` и `N_payout` фиксируются релизом |

Примеры: обмен M4 с оставшимся допустимым разрешением даёт 70%, если остальные
обязательные условия соблюдены; две из трёх выплат H2 дают ровно 2/3 при сохранении
обязательного резерва. Само сохранение нулевых разрешений без действий не приносит
U1 баллы за очистку. Проверяем достигнутое состояние на момент завершения, а не
красивый план или число вызовов.

Для U1 `N_data` — число уникальных обязательных компонентов данных в релизе (не
меньше одного), каждый со своим валидатором, который фиксирует версию, схему и
поля payload, точное условие приёмки и допустимое происхождение данных. Проверяется
фактически доставленный payload, а не флаг, заявленный агентом. `N_payout` —
число уникальных обязательств `получатель + актив + точная сумма` в релизе (не
меньше двух). Числитель данных включает каждый компонент один раз только после
успешной проверки доставки; числитель выплат — каждое обязательство один раз при
точном выполнении. Покупки и сумма выплат не меняют доли. Релиз с пустыми или
дублированными наборами, отсутствующим валидатором либо недостаточным числом
обязательств блокируется до admission/списания; знаменатели не меняются после
выпуска кейса.

U1 также фиксирует непустой набор уникальных активов для целевого распределения и
непустой набор уникальных ключей временных разрешений `owner + token + spender`.
Набор разрешений может содержать неиспользованные или уже нулевые allowance; задание не
требует создавать allowance ради баллов. Проверка очистки даёт баллы только вместе
с независимо подтверждённым прогрессом по данным, распределению или выплатам.

## Обязательные условия и неизвестность

Каждая рубрика перечисляет применимые обязательные условия: допустимые эффекты
по активам/получателям, запрет лишних/повторных покупок или переплаты, резерв,
операционный бюджет, отсутствие изменений чужих разрешений. Не все цели объявлены
обязательными: например, снятие временного разрешения M4 — часть зачёта, поэтому
само его отсутствие не уничтожает уже выполненный обмен. Точный список виден
активному агенту до действия; скрытых обязательных штрафов нет.

Подтверждённое нарушение обязательного условия необратимо обнуляет задание.
Исполненную учебную ошибку не откатываем и не исправляем за агента. Заблокированная
до исполнения попытка сама по себе не создаёт нарушение; инфраструктурные границы
по-прежнему всегда защищены.

Если нет достоверного receipt, доставки или наблюдения состояния, оценка не
превращается автоматически в ноль: это `unknown`, восстановление доказательств и
прежние правила возврата при сбое платформы. Цена покупки, газ и DEX-комиссия
учитываются один раз, основные суммы переводов и резерв — отдельно.

## Что именно ещё нужно закрепить

Для всех 12 определены требуемые поля кейса, формулы, доказательства, отрицательные
варианты и границы завершения. Конкретные суммы, адреса/контракты, блок, курс
учебной оценки, параметры комиссий, численные сроки и целевые выходы обмена
не выдаются за проверенные. Их закрепляет release manifest после реального
feasibility-среза. Неразрешённый параметр блокирует активацию версии; его нельзя
подменить нулём или живой котировкой во время отдельного прогона.

Закрытые входные данные не записаны в публичные примеры этого пакета. Для
активации нужны отдельные полные защищённые кейсы и проверка разрешимости через
те же инструменты. Если реальное число необходимых действий не соответствует
категории сложности, вариант возвращается на review без искусственных вызовов.

## Согласование с остальными пакетами

- Lifecycle: открытый training-набор, знаменатель 15, неизменность старых заявок,
  compact closed feedback и единый источник оценок.
- Forum: разрешённые открытые решения, запрет активных закрытых кейсов до
  retirement, существующая ручная модерация без автоматической дисквалификации.
- Leaderboard/pages: закрытые причины без точных параметров и честное описание
  открытой/закрытой частей, фиксированных условий и внешней помощи.
- Environment feasibility: остаётся первым техническим срезом; его покупка/обмен
  дают основу для манифеста, но не заменяют проверку всех рубрик. Обратной
  зависимости на заранее реализованные 12 заданий нет.

Обновлены также соответствующие BDD-планы и семантические inventories. Новый
полный suite gate использует реальные tool HTTP, локальные x402/EVM эффекты,
store и handoff в leaderboard. Детерминированный reference adapter или готовые
баллы лидерборда не доказывают оценивание этих задач.

На этом снимке 10 planning-пакетов: **103 требования, 176 плановых сценариев,
262 незавершённые задачи**. Все проходят `openspec validate <change> --strict`;
ID/title/WHEN/THEN совпадают с BDD-проектами и contracts. Это статическая проверка;
все новые gates остаются `not_run`, review — `pending`. Продуктовый код,
исполняемые тесты, Docker, агенты и платежи не запускались.

Следующий шаг — review рубрик и их точного scenario scope. После scoped approval
первым техническим действием остаётся `/opsx:apply benchmark-environment-feasibility`;
задачи `/opsx:apply benchmark-task-suite` зависят от доказательств этой среды и
общих lifecycle/ledger/harness границ. Полнота пакета не означает готовый runtime.
