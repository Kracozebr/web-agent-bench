## Intent

**Goal:** verify owner login/linking, invitation activation and open-registration transition through actual identity and downstream admission boundaries.

**Non-goals:** real payments, agent MCP implementation, bonus auto-grants, account mergers/unlinking, recovery redesign or public profile composition.

## Scenario design

All gates are mandatory `environment`. OID-SC-001–011 use actual local application/database/verifiers and declared browser/provider fixtures. OID-SC-012 separately requires actual Google and a selected browser wallet. A fixture or signature-library pass cannot replace that external integration.

## Semantic harness contract

`bdd-harness-proposal.json` is a review artifact, not the runtime manifest. It declares the boundary, named observations, negative variants and durable effects for every scenario. Merge reviewed contracts into the shared harness after explicit approval; an inventory count alone is insufficient.

## Execution design

- Reuse shared source selection, pytest-bdd, mapper registry, semantic audit and evidence identities from the lifecycle packet; do not sync this proposal to bypass active-delta tooling work.
- Planned mappers: `tests/bdd/mappers/test_owner_identity_and_pilot_admission_bdd.py`; planned adapter: `tests/bdd/adapters/owner_identity_and_pilot_admission.py`. No executable file is created by this packet.
- Require actual Fastify/PostgreSQL, real session and cryptographic wallet verification, actual Next.js pages and integrated agent-access/billing/funding authorization handlers where declared. No trusted-ID header, canned admission result or toy ledger substitutes for the boundary.
- Use declared isolated provider transport and ephemeral test signing material for local Google-contract cases. Verify actual correlation/claims rather than returning success from a fake verifier. Label every such trace local contract evidence, not actual Google.
- OID-SC-009/011 require real browser controls. OID-SC-012 additionally requires an actual dedicated Google test project/account, approved callback and selected browser wallet/profile, with actual login/activation/linking/return flows. Missing configuration or applications means blocked; do not ask for secrets in chat or place them in fixtures.
- No real token transfer, customer asset or production activation is required/authorized. A login signature is not a withdrawal proof, and an invitation is not a bonus grant.
- Exercise concurrent redemption, callback/session substitution, response loss, restart, expiry and registration-mode races through private test seams and actual durable transactions.
- Observe owner/provider/wallet identity bindings, nonce/operation/redemption identities, session state, admission and policy revisions, downstream denied/allowed effects and unchanged source balances.
- Evidence must redact Google user data, cookies, OAuth tokens, invitation plaintext and wallet/private key material. Preserve sanitized raw paths/hashes; inspect secret absence without printing candidates into logs.
- Replay compares stored decisions and reports missing/divergent evidence without reauthenticating, redeeming, issuing bonuses or repeating product actions.
- Missing real verifiers, domain dependencies, browser, selected provider/wallet or any required named observation is `blocked` with a reason. Mandatory blocked/skipped gates prevent sync/archive.
- Planning check: `openspec validate owner-identity-and-pilot-admission --strict`. Future execution requires semantic audit, JUnit and source/Git/harness/contract hashes. No executable acceptance ran during planning.
