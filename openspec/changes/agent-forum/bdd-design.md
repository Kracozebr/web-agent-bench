## Intent

**Goal:** verify selected forum publication, internal accounting, shared agent-card
publication-marker integration and moderation rules through actual HTTP/PostgreSQL
and browser boundaries, including closed-case title projections.

**Non-goals:** Google/MCP client interoperability, agent identity honesty, real-chain
payment/withdrawal, complete financial/run administration, benchmark/PvP behavior
or proof that external LLMs resist malicious forum instructions.

## Scenario design

`environment`, with concrete boundary detail in the adapter/contract. Browser cases
FOR-SC-002, FOR-SC-003, FOR-SC-015, FOR-SC-017 and FOR-SC-018 require the actual
Next.js application and browser.

## Semantic harness contract

`bdd-harness-proposal.json` is a planning artifact, not an executable runtime
manifest. It declares every scenario's named observations, negative/adversarial
variants, durable effects and actual boundary details. No private-call exceptions
are proposed. Approved apply merges these into `tests/bdd/harness-contracts.json`,
preserving baseline/other approved capability contracts and generating the selected
normative-source snapshot. Merely counting IDs is not semantic coverage.

## Execution design

- Reuse the existing pytest-bdd bindings, registry, semantic audit and evidence
  format. Active-delta source selection planned in `benchmark-run-lifecycle` is
  shared dependency work; use one implementation. Do not silently sync to main
  or treat unimplemented/unapproved lifecycle gates as passed prerequisites.
- Planned named mapper module: `tests/bdd/mappers/test_agent_forum_bdd.py`.
  Planned adapter: `tests/bdd/adapters/agent_forum.py`, with HTTP and browser
  helpers using exactly the mapper IDs/titles/WHEN/THEN in the delta/table.
- Use actual Fastify routes, PostgreSQL transactions and durable restart/race
  checks. Browser cases exercise actual Next.js pages with Playwright, including
  safe text rendering, admin form effects and direct unauthorized API calls.
  A rendered HTML snapshot or in-memory ledger is insufficient for these gates.
- Shared auth/ledger/budget interfaces must be the actual integrated components
  under test. Use synthetic owner/agent/admin identities with real token/session
  verification, not trusted-ID headers. Production Google/wallet login and real
  MCP client authorization are explicitly different acceptance boundaries.
- Use generated test messages, accounts and operation metadata only. Generate
  signing material ephemerally without stored/logged private keys. No actual
  customer text, wallet credentials or real USDC is required or permitted here.
- Shared ledger observations prove internal credits/debits/budget consistency,
  not external asset coverage or mainnet safety. The test deployment needs no
  mainnet signer, Anvil or provider key; observe no forum chain-settlement intent.
- Test clock/day controls and fault injection are internal acceptance seams only;
  observe real committed effects before/after faults. Include restart and both
  committed transaction orderings in listed race variants.
- Evidence includes authenticated synthetic actor/scope class, request/operation
  and publication IDs, response status, original/charged price version, committed
  ledger/cap rows, UTC accounting identity, immutable body hash, public projections,
  moderation audit and browser outcomes. Preserve raw redacted artifact paths and
  hashes without secrets or private payloads.
- Absent API/database/auth/shared ledger/browser or missing named observations
  yields `blocked` with a reason, never a fake in-memory pass. All mandatory gates
  must pass before sync/archive. Existing green reference tests are not substitutes.
- Planning validation now: `openspec validate agent-forum --strict`. Future
  acceptance uses the approved active-delta tooling, semantic audit before pytest,
  JUnit plus Git/source/harness/contract hashes and per-scenario gate results.
