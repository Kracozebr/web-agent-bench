## Intent

**Goal:** verify permanent owner funding, automatic verified deposits, safe-stage service spending, finalized-only withdrawals, owner proof, durable custody execution and shared accounting.

**Non-goals:** production/mainnet activation, real customer funds, new prize modes, full identity/MCP onboarding or proof of economic safety.

## Scenario design

All scenarios are mandatory `environment` gates. BAP-SC-001–019 require the actual application HTTP/PostgreSQL boundaries and, where relevant, Anvil token execution. Their explicit finality gateway is controlled test input, not Base finality evidence. BAP-SC-011 and BAP-SC-018 additionally require actual browser pages and verification. BAP-SC-020 separately requires actual CDP and Base Sepolia resources; a fixture cannot satisfy it.

## Semantic harness contract

`bdd-harness-proposal.json` is a review artifact, not the runtime manifest. Every scenario declares its boundary, required named observations, negative/adversarial variants and durable effects. After explicit approval, merge contracts into the shared runtime manifest and generate mirrors from the selected active delta. An ID count alone is not semantic coverage.

## Execution design

- Reuse the existing pytest-bdd, mapper registry, semantic audit and evidence format, plus shared active-delta selection planned in benchmark-run-lifecycle. Do not sync a proposal merely to make the current main-only harness discover it.
- Planned mappers: `tests/bdd/mappers/test_base_account_payments_bdd.py`; planned adapter: `tests/bdd/adapters/base_account_payments.py`. These files do not exist as part of this proposal.
- Exercise actual Fastify/PostgreSQL transactions, cryptographic owner proof verification, scoped roles and actual Next.js pages. No trusted-owner header, public auth bypass or toy ledger substitutes for the declared boundary.
- Actual forum and coordinator cash consumers must share cash allocations with withdrawals; preserve the bonus packet's source identity and full nominal budget rules. An evaluator fixture does not prove the twelve task rubrics.
- Use ephemeral synthetic identities and local token balances. Controlled RPC finality, clock, provider transport and failure seams must remain private acceptance infrastructure and appear in evidence as controlled inputs. Never represent a local CDP transport contract fixture as a live provider call.
- For passkey verification, use a declared virtual WebAuthn authenticator through the actual browser/server path; evidence does not establish compatibility with all physical devices.
- Observe event/block identities, source lots, reservations, proof consumption, nonce/transaction relationships, gas/sweep purpose and terminal postings across response loss, process restart and concurrency.
- For BAP-SC-012 use exact base units at the minimum and on either side, whole versus partial subminimum amounts, zero, unrelated safe/bonus/held value and concurrent availability changes. Observe atomic admission, unchanged signed amount, retained policy/version/exception basis and no proof consumption or signing intent on rejection. BAP-SC-018 observes actual owner threshold display and authorized versus unauthorized audited admin configuration changes.
- Before BAP-SC-020, configure an actual dedicated CDP account, Base Sepolia RPC/token/test funds and the reviewed provider methods/policies. Probe real signing and test-asset submission, observe actual safe/finalized heads and receipt identity, and reconcile the same intent without an extra payment. No mainnet assets or production activation are authorized.
- Provider credentials, Wallet Secret, private keys, passkey material and raw protected signed payloads must not enter prompts, logs or evidence. Redact user data; retain sanitized raw observation paths and hashes.
- Missing API, database, auth, integrated cash consumers, browser, external test account/funds, supported head tags or named observations is `blocked` with a reason. Unknown provider/chain results remain unknown; local success cannot waive the external gate.
- Planning validation: `openspec validate base-account-payments --strict`. Future execution requires source/Git/harness/contract hashes, semantic audit, JUnit and per-scenario evidence. No executable acceptance has run during proposal authoring.

## Approval boundary

Approval authorizes only these 20 scenarios and variants, their named mappers/adapters, shared cash provenance, payment/recovery web/API surfaces and the declared local plus dedicated testnet integration. It does not authorize production deployment, real customer funds, new assertions or PvP settlement. Scope/assertion changes return to review.

**Decision:** pending.
**Decision reference:** the user selected an administrator-configurable initial 1-USDC withdrawal minimum with a whole-positive-withdrawable-remainder exception below the threshold. These amount rules do not waive owner confirmation, finalized funding or reservations. The user also selected permanent EOA accounts, CDP, automatic verified deposits, fresh wallet/passkey owner confirmation, platform-paid withdrawal gas, initial method setup and backup/manual recovery. The user also confirmed service availability after `safe`, withdrawal after `finalized`, an affected-owner cash-spend/withdrawal pause on proven deposit canonicality loss, and a new-withdrawal pause during manual recovery with ordinary services/bonuses available. The finalized terminal/release rule in this revision is an engineering default; allocation/signing feasibility and full implementation approval remain open.
