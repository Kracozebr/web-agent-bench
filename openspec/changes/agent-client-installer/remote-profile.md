# Remote OAuth MCP implementation profile

This is the configured implementation profile for the approved active ACI delta. It is not a native-client qualification or external deployment claim.

`OID_MCP_TRANSPORT_PROFILE=remote-oauth-v1` selects Streamable HTTP with MCP `2025-06-18` or `2026-07-28`. The modern profile requires matching method/name routing headers; the legacy profile retains its actual wire semantics and SSE response. Application name/version is metadata. The existing default strict profile, pinned local manual Codex profile, and older beta profile retain their existing boundaries. A beta manifest can explicitly select `remote-oauth-v1`; runtime and manifest must match. Only enabled, natively verified client surfaces may enter a cohort support claim; other targets remain unverified.

The configured public origin determines the canonical `/api/agent/mcp` endpoint and the same exact `/api/agent/mcp` OAuth resource for this remote profile. Older profiles retain their `/api/agent` resource. Authorization and token audiences remain singular and exact; no resource aliases are accepted. Native setup must not add a second `--oauth-resource` value when the client already supplies the endpoint resource. Production requires HTTPS; development/tests can explicitly use loopback HTTP. No external hostname has been selected or verified here. No add/import deep link has been verified, so setup returns an honest URL fallback and no native-add URL. No local package, bridge, process, provider credential, or platform-written client configuration is introduced.

Registration initially uses pre-registered public OAuth clients with exact callbacks, S256 PKCE, and explicit browser owner/agent consent. Setup includes the configured public client ID, callback, resource, and scopes; URL-only setup is not claimed to work in every client. Native Codex CLI 0.165.0 help exposes `--oauth-client-id`, `--oauth-resource`, and login `--scopes`; that help is configuration evidence, not a successful connection. [Official OpenAI authentication documentation](https://developers.openai.com/plugins/build/auth) describes pre-defined clients alongside DCR/CIMD. DCR and arbitrary metadata URL fetching remain disabled.

Remote consent requests `agent:operate` and, for renewable access, `offline_access`. The latter permits renewal and enables no business action. Access tokens last one hour. Refresh credentials rotate with a 30-day inactivity bound; an active connection renews automatically. The same verified grant ID remains the connection identity across token rotation. Permissions, limits, resource, owner/agent identity, and access generation remain under existing AAP authority. A 30-second response-loss window recovers the same provider-issued credential pair from its encrypted database replay record. Replay outside that window revokes only the affected connection family. The wrapper checks current owner/grant/generation before consulting cached provider replay and serializes refresh with AAP revocation. A valid refresh can recover a stale grant-expiry projection after interruption; it cannot recover revoked access. An internal bounded queue reserves database pool headroom for the pinned provider's separate adapter checkout.

Health comes from an actual authenticated `identity.preflight` MCP call, with optional identity hints checked against the grant-derived principal. Its durable audit timestamp and negotiated protocol establish the last successful check, not proof of current network availability or client-family qualification. After five minutes without another check the UI labels the observation old/offline. No run, reservation, queue slot, task operation, publication, or financial effect is created by preflight or renewal.

The browser can include `selectedConnectionId` when creating an existing BRL launch intent. The owner operation's payload hash includes the stable grant ID. Creation validates it under AAP locks and atomically writes one immutable `agent.connection.intent_bound` audit event with the intent. Acceptance checks exactly zero or one binding and denies a different connection before run/operation replay or new admission. Legacy requests without a selected connection retain the existing BRL contract. Pending intents reserve and charge nothing. All acceptance, quote, reservation, queue, and once-only business effects remain BRL-owned.

Implementation checks use a newly created disposable PostgreSQL database and the real pinned OAuth provider/Fastify MCP handler. They cover rotation, response loss, concurrent refresh, scoped replay invalidation, stale expiry recovery, schema-valid MCP preflight, HTTP revoke, and selected-connection once-only admission. They do not establish browser initiation, a native OAuth client, restored-checkpoint fencing, or an external HTTPS service. The eight mandatory environment gates remain separate.

Activation needs the existing unified checkpoint/restore boundary before running the prepared migration. It expands the grant-revocation reason constraint and, only for the remote profile, provisions explicit refresh grant/scopes for the configured OAuth clients/resource. No live migration or application restart was performed by this implementation agent.

## External invalidation and restored startup

The operator owns an invalidation journal, a separate monotonic head/floor file, and the expected journal ID outside the database, private-data directory, and ordinary checkpoint restoration. New files require explicit initialization; a missing file is never silently replaced. Each scoped revocation, agent-wide generation fence, and refresh consumption has a hashed operation reference and durable intent before acknowledgement. Files use private permissions, checked paths, exclusive locks, atomic replacement, and fsync. A divergent, truncated, tampered, missing, or observed-regressed journal/floor fails closed. Raw credentials are never stored; refresh consumption records only the provider's SHA-256/base64url verifier digest.

Startup reconciliation reads and releases the external-file snapshot before SQL locking, applies connection fences or existing AAP generation/cancellation-outbox effects, records the reconciled watermark in the existing audit table, then verifies the external head has not changed. A missing or still-active consumed refresh record in the restored database represents uncertain/stale rotation: invalidate only that connection and require reauthorization. An already rotated record preserves the legitimate encrypted 30-second retry. Live JWT resolution and refresh also consult this external authority; an unresolved consumption cannot authorize business access before reconciliation. Unaffected connections, agents, admitted runs, reservations, and ledger entries remain unchanged by scoped reconciliation.

The API and worker must not listen before successful reconciliation. For a database restored with default transaction read-only enabled, use a separate maintenance-only connection for the narrow security reconciliation; do not enable general API writes to perform it. Server-required configuration and backup watermark integration are separate wiring owned by the runtime/restore workflow. The journal and its floor must never be rolled back together with an old checkpoint. Hash chaining does not establish freshness if an operator replaces both external files and the database with matching old versions; authoritative external state must survive that restoration failure domain.

Disposable component tests exercise real OAuth/HTTP 401 fencing, journal write/floor interruption, scope preservation, and PostgreSQL rollback reconciliation. They are not physical cold-restore acceptance evidence; that environment gate still needs the coordinated checkpoint/restore capture and independent observer.
